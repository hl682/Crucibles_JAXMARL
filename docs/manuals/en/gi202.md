# GI202 · Counterweight Foundry

Deliver all three tagged crates by loading the beam and bringing both ends to row seven.

## Objective and gameplay

Deliver all three tagged crates by loading the beam and bringing both ends to row seven.

One worker's winch request changes beam tilt, occupied cells, partner control positions and cargo risk. Carrying or removing shared counterweights changes peer lift feasibility; nearby bracing can substitute for weight support and reduce tension at an individual work cost.

- Operate a winch from its moving side pad with empty hands. North/south requests act jointly; loaded ends need a mounted weight or another worker's brace.

- The five stepped beam cells block walking. Beam motion that would overlap a worker is cancelled; jam shows this physical obstruction.

- Pick up nearby loose crates or any unheld weight, including mounted weights. One object fits in a worker's hands; dropping uses the worker's cell.

- Loading requires a carried crate beside the centre, an empty beam and endpoint difference at most one. A level loaded beam at row seven delivers its crate.

- Moving with unequal endpoint rows or unequal weight counts adds tension. A brace reduces tension by two; ordinary rest reduces it by one.

- Unbraced tilt of two or more drops a loaded crate to the floor. Tension eight breaks a loaded crate and ends the shift in failure.

- Shared delivery reward and tagged-owner bonus compete with individual work costs. Bracing, balancing weights and following both winches are alternative dependencies.

- All native observations are public. Scripts remain unexecuted hypotheses; human and policy controls use the same actions.

Ending: Success when all three crate statuses equal delivered. Failure when any crate is lost or beam tension reaches eight, unless success. Otherwise cap at 160 nonterminal transitions.

## What this game explores

Resource commons & externalities: An action changes a persistent resource or burden that another role also encounters. Compare extraction with maintenance and record the downstream resource trajectory.

Complementary production & service: A useful outcome requires ordered stages, scarce equipment or another role's capability. Measure real completed products and resource circulation rather than counting intermediate actions as success.

Joint transport & shared access: Positions, load geometry, occupancy and persistent access constrain whose action can succeed next. Distinguish physical handoff, shared controls and simultaneous force from a cosmetic cooperation label.

These are questions supported by rule structure, not observed learning effects.

## Reinforcement-learning integration

```python
import jax
from crucibles_jaxmarl import make

env = make("gi202")
key = jax.random.PRNGKey(0)
key, rk, ak, sk = jax.random.split(key, 4)
obs, state = jax.jit(env.reset)(rk)
actions = env.sample_actions(ak, state)
obs, state, rewards, dones, info = jax.jit(env.step_env)(sk, state, actions)
done = dones["__all__"]
```

Observations are float32 vectors of width 182; actions are scalar int32; masks have 13 entries. Supply all 3 roles each transition. Masked sampling is an engineering reference, not a trained learner.

`step_env` retains terminal data without reset. `step` performs outer autoreset and keeps terminal data in `info["raw_state"]` and `info["raw_observation"]`. Use `dones["__all__"]` for episode boundaries; separate completion, failure and time limit in analysis.

JIT or vmap equal identities and shapes. Split independent reset, policy and transition keys. Group different shapes explicitly; do not shrink the population or horizon. Host rendering stays outside training.
