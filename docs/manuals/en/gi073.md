## Objective and gameplay

Complete all four receivers' ordered three-colour demands using the finite 8-blue/8-amber source.

Technicians must be orthogonally adjacent to operate physical fixtures. Pulses advance along the rail tree using old turnout states, are consumed by arrivals, and reveal the next local demand only after a match.

- Four technicians walk to real source/turnout fixtures to operate them. Ordinary rail cells remain walkable on a separate technician layer.

- A launch spends one of eight charges of that colour. Existing pulses advance one edge per step; a new pulse starts at the source until the next step.

- A departing pulse reads the OLD turnout mode. A same-step SET applies only to subsequent departures.

- Only the current receiver demand is visible nearby. Correct colours advance its three-step prefix; wrong or unnecessary arrivals consume the pulse without progress.

- Role maps and entity locations must use their actual radius-two visibility masks. Full-state/debug views are privileged; future recipes are never scene attributes.

- Event outcomes, pulse identities and rail direction annotations are debug diagnostics, not extra policy columns. The policy receives only the declared 557 columns.

- Blue and amber groups are disjoint masks over the same sixteen physical slots. Follow unique pulse IDs when a consumed slot is reused.

- Arrival events carry actual from/to nodes. No radio, collision, recall, fabricated delivery or hypothetical successful-run animation is permitted.

- All receivers complete means success; empty stock with no pulses and incomplete receivers means failure. Natural outcomes precede the 512-step limit.

- Terminal states are absorbing. Consume a recorded event only once per t; full-state diagnostics must not masquerade as a role observation.

Ending: Success when every receiver progress is 3; natural failure when both source stocks are empty and all pulses absorbed with work remaining. Natural completion precedes the 512-step limit.

## What this game explores

Information, sensing & communication: Who knows a fact, when it was measured, and whether it was communicated are separate state variables. Test memory or communication using only the same role-visible evidence.

Complementary production & service: A useful outcome requires ordered stages, scarce equipment or another role's capability. Measure real completed products and resource circulation rather than counting intermediate actions as success.

Joint transport & shared access: Positions, load geometry, occupancy and persistent access constrain whose action can succeed next. Distinguish physical handoff, shared controls and simultaneous force from a cosmetic cooperation label.

These are questions supported by rule structure, not observed learning effects.

## Reinforcement-learning integration

```python
import jax
from crucibles_jaxmarl import make

env = make("gi073")
key = jax.random.PRNGKey(0)
key, rk, ak, sk = jax.random.split(key, 4)
obs, state = jax.jit(env.reset)(rk)
actions = env.sample_actions(ak, state)
obs, state, rewards, dones, info = jax.jit(env.step_env)(sk, state, actions)
done = dones["__all__"]
```

Observations are float32 vectors of width 557; actions are scalar int32; masks have 9 entries. Supply all 4 roles each transition. Masked sampling is an engineering reference, not a trained learner.

`step_env` retains terminal data without reset. `step` performs outer autoreset and keeps terminal data in `info["raw_state"]` and `info["raw_observation"]`. Use `dones["__all__"]` for episode boundaries; separate completion, failure and time limit in analysis.

JIT or vmap equal identities and shapes. Split independent reset, policy and transition keys. Group different shapes explicitly; do not shrink the population or horizon. Host rendering stays outside training.
